## حدود العمل

دورني تطبيق Next.js واحد بواجهة React وواجهات API وقاعدة Supabase. ليس Flutter ولا غلاف تطبيق أصلي. التثبيت والإشعارات عبر PWA. مشروع الإنتاج المقصود هو `ppflwbwnxxmfzdfckhlk` وخدمة Render هي `srv-dam30n740ujc73ff8e2g`. أي مشروع آخر، خصوصاً Equal ID، خارج النطاق. لا تُنسخ أسرار الإنتاج أو بيانات العملاء إلى التوثيق أو الاختبارات.

## خريطة التطبيق

| المسار | المسؤولية |
| --- | --- |
| `/login`، `/auth/callback`، `/reset-password` | الحسابات وتأكيد البريد واستعادة كلمة المرور |
| `/app` | حساب المالك والسيارات والبطاقات والبلاغات |
| `/t/[token]` | المسح وإرسال بلاغ دون إظهار هوية صاحب السيارة |
| `/status/[token]` | متابعة البلاغ عبر رابط محدود الصلاحية |
| `/partner` | الشركة والدفعات والتفعيل والتنزيلات |
| `/support` | متابعة التذاكر بواسطة موظفين بصلاحيات قائمة |
| `/admin` | عمليات الإدارة المقيدة بالصلاحيات |
| `/admin/setup` | تفعيل أول حساب `SUPER_ADMIN` مرة واحدة برمز Render السري |
| `/install` | تعليمات تثبيت التطبيق |

الشريط السفلي ثلاثة أقسام فقط: الرئيسية، سياراتي، التنبيهات. القائمة الجانبية تبقى للدعم والدليل والخصوصية والإعدادات والخروج. `lib/owner-navigation.ts` يدير روابط الأقسام والرجوع، و`components/owner-disclosure.tsx` يدير البطاقات القابلة للطي. تبقى النماذج مركبة عند تبديل الأقسام؛ هذا لا يعني حفظ المسودات بعد إعادة تحميل الصفحة. الحفظ الدائم يحدث عند نجاح عملية الحفظ على الخادم.

## تدفق البيانات

1. الشركة الجديدة تسجل طلباً بحالة `PENDING`. المدير وحده يعتمدها ويحدد هل يسمح لها بالإصدار المباشر والحد اليومي؛ الصلاحية والحدود تتحقق على الخادم وقاعدة البيانات.
2. المالك يضيف سيارة ويطالب ببطاقة باستخدام بيانات التفعيل. رابط المسح ليس رمز المطالبة.
3. المسح يقرأ وصف السيارة المسموح فقط، ثم يحفظ البلاغ عبر API.
4. قائمة المالك تتحدث دورياً؛ وصول Push مسار منفصل يعتمد على الاشتراك والعامل.
5. رد المالك يحفظ في المنظومة ويظهر في رابط متابعة الشاكي.

`app/api/` نقطة دخول العمليات. `lib/server/` للخدمات والتحقق، و`lib/supabase/` لعملاء الاتصال. لا تُنقل صلاحيات أو مفاتيح إدارية إلى المتصفح. مراجعة الملكية والصلاحيات لا تعتمد على إخفاء زر في الواجهة.

## ما يجب الحفاظ عليه

- `components/push-settings.tsx` و`app/api/push/` والعامل وملفات خدمة الإشعارات: لا تغيّرها ضمن تعديل شكلي.
- لا تبدّل مفاتيح VAPID أثناء نشر واجهة؛ الاشتراكات الحالية تعتمد عليها.
- احتفظ برابط `/app?tab=alerts` الذي يفتح من الإشعار.
- لا تُخزّن صفحات الحساب أو API في كاش خدمة العامل.
- لا تعاود عمليات الكتابة تلقائياً بعد انقطاع الاتصال؛ ربما تمت الكتابة رغم ضياع الرد.
- SQL للاختبارات ذات rollback ليس ترقية إنتاج. راجع سجل الترحيلات قبل تطبيق أي SQL.

راجع `WEB_PUSH.md` لتفاصيل الإرسال و`OWNER_WORKSPACE.md` لقواعد السيارات والبطاقات والتذاكر والجلسات.
راجع `ADMIN_CONTROL_PLANE.md` لإنشاء المدير الوحيد، دورة اعتماد الشركات والموزعين، وحدود صلاحيات الإدارة.

## حدود المنتج الحالية

الدخول بالبريد وكلمة المرور. SMS وWhatsApp ليسا قناتين مفعّلتين هنا. الواجهة عربية. تغيير البريد ليس نموذجاً متاحاً للمستخدم؛ يُحال إلى الدعم دون وعد بتنفيذ تلقائي. طلب حذف الحساب تذكرة مراجعة فقط، لا حذف ولا تعطيل تلقائي. نشر الشروط وسياسة الخصوصية يتطلب وثائق معتمدة؛ لا تُختلق موافقات. ردود الدعم تُتابع من التذاكر ولا تُعد إشعارات Push للدعم ميزة منفذة.

## التشغيل والتحقق

استخدم Node 22 وملف القفل مع `npm ci`. راجع `.env.example` لأسماء المتغيرات فقط. لا تطبع `.env.local` أو أسرار Render. إعداد قاعدة جديدة يحتاج مطابقة سجل الترحيلات مع تغييرات SQL اللاحقة؛ ترحيل الأساس وحده غير كافٍ.

نفّذ كل أمر وتأكد من نجاحه منفرداً:

```text
npm run lint
npm run typecheck
npm test
npm run build
```

بعض الاختبارات عقود مصدر ثابتة، وليست محاكاة كاملة للمتصفح أو إثبات وصول إشعار. لا تستبدل بها اختبار القبول التالي.

## المرحلة التالية: قبول النسخة ثم النشر

- اختبر عرض الهاتف والفاتح والداكن ولوحة المفاتيح: ثلاثة أزرار تنقل، قائمة جانبية، فتح وطي البطاقات، وعدم حجب الأزرار أسفل الشاشة.
- اختبر الرجوع وروابط الأقسام واحتفاظ النماذج بالقيم أثناء التنقل.
- بحسابات اختبار فقط: حفظ سيارة ثم إعادة التحميل، تفعيل بطاقة، بلاغ من جهاز ثانٍ، رد المالك، وتحديث حالة الشاكي.
- على جهاز فعلي: اشتراك Push قائم وجديد، وصول أثناء إغلاق التطبيق، والنقر لفتح التنبيهات. لا تغيّر اشتراك مستخدم فعلي لغرض الاختبار.
- راجع الفرق ثم انشر commit معروفاً. تحقق أن Render يعرض نفس commit بحالة Live، وليس مجرد نجاح البناء المحلي.
- اختبر `/login` و`/install` والمسارات الخاصة بعد النشر. سجل commit والوقت ونتائج الأجهزة وأي قيد متبقٍ.
- عند تراجع الواجهة، أعد نشر commit السابق؛ لا تسترجع قاعدة البيانات أو تحذف بيانات العملاء لتراجع واجهة.

لم تُنفذ اختبارات الهاتف أو النشر بواسطة كتابة هذا المستند. لا تُعتبر أي خانة قبول ناجحة دون دليل منفصل.
